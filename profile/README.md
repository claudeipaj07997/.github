<h2>一、四类现象，四条分支</h2>
<p>现象描述越具体，分支越容易对上。"用不了"这种描述没法排查，至少要拆成：连不上、能连但 IP 不对、能连 IP 对但被拦、部分账号正常部分异常。四句话对应四条互不重叠的路径，先归类再往下走。</p>

<h2>二、分支一：出口连不上</h2>
<h3>先分是鉴权问题还是链路问题</h3>
<p>用 curl -v -x socks5h://用户:密码@网关:端口 https://ipinfo.io/ip 跑一次，看报错落在哪。407 是鉴权失败，多半是密码改了没同步或账号被停；连接超时是链路或端口问题，先换端口再换网关；能连上但返回空，多半是 DNS 没走代理，加 -h 参数交给代理解析。</p>
<h3>白名单是最常见的坑</h3>
<p>不少服务商用 IP 白名单代替账号密码。换了办公网出口、或者本机公网 IP 变了，白名单就失效，表现和"线路坏了"一模一样。养成习惯：任何"连不上"先查自己的公网 IP 有没有变，再去查服务端。</p>
<h2>三、分支二：IP 漂了</h2>
<p>家庭宽带多为动态分配，路由器重启、运营商侧维护、长时间空闲回收，都会导致公网 IP 变化。漂移本身不是故障，没有感知才是。配一个每分钟请求一次 ipinfo.io/ip 的脚本，把结果和时间戳写进日志，变化即告警。</p>

<h3>漂移之后要不要通知账号侧</h3>
<p>分情况。同城同运营商内的变动，通常可以接受，记录即可；跨城市、跨运营商跳变，就要评估是否影响账号环境，必要时暂停使用并观察。规则提前写进运维文档，别临场拍脑袋。</p>
<h3>固定 IP 也不是绝对不动</h3>
<p>所谓固定 IP 家宽，多数是在合约期内保持分配不变，运营商侧调整或迁机仍可能变。合同里通常会写明变更通知义务，采购时把这条看清，出问题时才有依据。</p>
<h2>四、分支三：能连但被拦</h2>
<h3>先排除环境矛盾</h3>
<p>IP 归属地和时区、语言、支付资料对不上，是最容易被忽略的一类。比如出口在德国，浏览器时区是 UTC+8，界面语言是中文，三处都不一致。这类情况不需要"处理"，只需要把环境调回自洽。</p>
<h3>再看邻居密度</h3>
<p>同一条 /24 段里如果挂了几百个地址、混着大量可疑域名，说明这段被反复用过，出口信誉会受影响。查法：把 IP 拿去 ipwho.is 看 connections，再对照公开的段信息，邻居太密就换段。</p>
<h3>最后看行为节奏</h3>
<p>同一出口下多个账号在同一分钟登录、同一秒发起相同请求、每天固定整点操作，这些规律性本身就是异常信号。把登录时间打散到自然分布，比换十条线都有效。</p>
<h2>五、分支四：多账号串味</h2>
<h3>分组要能一眼验证</h3>
<p>台账三列就够：账号、绑定出口、分组标签。每周对一次，重点查"一个出口挂了多个分组"和"一个分组跨了多个地区"这两种情况——前者是串味高发区，后者会让资料自相矛盾。</p>

<h3>监控配到什么程度够用</h3>
<p>三个指标就够起步：端口可用率、出口 IP 变化次数、验证码触发率。前两个用脚本采，第三个靠人工记录。三者同时抬头，说明不是单点问题，要按出口段整体评估，而不是一个个换号。</p>
<h2>常见问答</h2>
<h3>出口 IP 一天变两次，需要换服务商吗？</h3>
<p>答：先看变化范围。同城同运营商内变动通常可接受，记录并观察即可；如果是跨地区跳变，或者变化后账号立刻出现异常，才考虑更换线路。</p>
<h3>白名单和账号密码鉴权，哪个更稳？</h3>
<p>答：白名单更省事但依赖本机公网 IP 固定，一旦办公网出口变化就会失效；账号密码鉴权灵活，但要防泄露。实际部署常见做法是两者叠加，白名单兜底、密码做二次校验。</p>
<h3>怎么判断是出口被标记，还是账号本身的问题？</h3>
<p>答：做交叉验证。同一账号换一条干净的出口试，如果恢复正常，问题在出口；同一出口下换另一个账号试，如果同样异常，问题在出口；两边都异常，再回到账号和环境侧排查。</p>
<h3>监控脚本跑在哪比较合适？</h3>
<p>答：跑在一台长期在线的小机器上，独立于代理链路，这样出口挂了也能发出告警。别把监控和业务放同一台机器，否则一起挂的时候你什么都不知道。</p>
<h2>合规提示</h2>
<p>本文的排查方法用于自有账号与自有网络的日常运维，适用于跨境办公、研发测试等正当场景。使用代理服务应遵守所在地法律法规及服务商条款。</p>
<p>监控与日志采集应限于自身业务所需范围，不应记录他人账号、密码等敏感信息；涉及个人数据的处理需符合相关规定。</p>
<p>请勿利用多账号环境从事批量注册、虚假交易或规避平台规则的行为。账号资料与支付信息应真实有效。</p>
